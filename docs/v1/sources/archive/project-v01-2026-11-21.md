# PsiOS 总体规划草案

**版本：** Draft v0.1  
**日期：** 2026-11-21  
**项目类型：** Agent-Native Operating System  
**开发策略：** 长期迭代、模块化建设、统一源码、多发行版构建  
**状态：** 架构讨论稿，尚未完成全部技术选型

---

## 一、项目定位与总体目标

### 1.1 项目定位

PsiOS 是基于 Linux 内核构建的 Agent-Native 操作系统。

它不仅提供传统操作系统的计算、存储、网络、桌面和应用管理能力，还将 AI Agent 作为操作系统的一等公民。

Agent 不应只是一种普通的聊天应用，而应当能够在用户授权下，理解、查询和操作操作系统提供的各类资源。

PsiOS 同时保持传统操作系统的完整可用性：用户可以不依赖 Agent，直接通过桌面、WebUI、CLI 和常规应用完成工作。

### 1.2 六项目标

1. **原生 Agent**：提供系统级 Agent Runtime、任务执行、工具访问、多 Agent 协作及长期任务管理。
2. **开放 Agent 生态**：允许第三方 Agent 框架、CLI Agent、远程 Agent 与原生 Agent 共同使用系统能力。
3. **统一容器应用平台**：可安装应用、系统扩展和可选服务原则上使用隔离执行环境，统一管理生命周期。
4. **统一数据与存储基础设施**：管理文件、存储卷、对象、数据集、索引、快照及备份，不重复保存不必要的数据副本。
5. **原生集群能力**：所有版本均支持加入集群，能够共享受授权的计算、数据与 Agent 服务。
6. **桌面和服务器一体化**：以统一核心支持轻量节点、服务器与完整 KDE 桌面。

### 1.3 明确不做的事情

- 不从零开发 Linux 内核。
- 不以保持旧 XeLab ABI、API 或数据库格式兼容为目标。
- 不要求所有设备都在本地部署 LLM。
- 不强制将 Linux 内核、驱动、KWin 等核心宿主组件容器化。
- 不强制安装知识库、数据集引擎或大型 AI 模型。
- 不在第一阶段重造完整的容器引擎、分布式文件系统或 Kubernetes。

## 二、三种基础发行版

PsiOS 初期正式提供三种基础发行版，均使用同一套 PsiOS Core。

| 发行版 | 定位 | 默认运行环境 | 典型用途 |
|---|---|---|---|
| **PsiOS Helium** | 精简版 | 最小宿主、CLI、WebUI、轻量服务 | VPS、边缘节点、轻量 Agent、集群 Worker |
| **PsiOS Neon** | 服务器版 | Headless 服务、容器、存储与计算管理 | NAS、服务器、AI 计算、集群基础设施 |
| **PsiOS Argon** | 桌面版 | KDE Plasma、Wayland、WebUI、桌面应用 | 个人电脑、工作站、图形 Agent、Computer Use |

### 2.1 统一能力要求

三个发行版都必须具备：

- PsiOS Core 和统一 API。
- 原生 Agent 运行能力。
- 第三方 Agent 接入能力。
- OCI 应用执行能力。
- 基本存储与权限管理。
- 加入集群与接受集群任务的能力。
- PsiOS Shell 管理入口。

不同发行版的区别是默认组件、部署方式和用户交互场景，而不是按照硬件性能划分功能权限。

### 2.2 扩展角色

集群管理器、存储服务器、GPU Worker、模型推理服务器、数据节点、自动化控制器等，属于可配置的节点角色，不新增基础发行版。

例如：

- Neon 可以是集群 Controller，也可以只提供存储。
- Helium 可以承担轻量 Worker 或网关角色。
- Argon 可以是个人桌面，也可以向集群提供 GPU 算力。

## 三、总体系统架构

建议采用五层架构。

```text
┌───────────────────────────────────────────┐
│                  用户入口                  │
│ KDE Plasma | PsiOS Shell | CLI | SDK      │
├───────────────────────────────────────────┤
│              PsiOS System API             │
│ Resource API | Identity | Policy | Audit │
│ Tool Gateway | Agent Bus | Cluster API   │
├───────────────────────────────────────────┤
│                系统服务层                 │
│ Agent Runtime  | Workload Manager         │
│ Storage Service| Task & Event Engine      │
│ Desktop Service| Model Gateway            │
│ Dataset Service(可选) | Knowledge(可选)    │
├───────────────────────────────────────────┤
│                工作负载层                 │
│ OCI容器 | Flatpak | Agents | Skills       │
│ 数据服务 | 扩展插件 | 用户应用             │
├───────────────────────────────────────────┤
│               最小宿主底座                │
│ Linux Kernel | systemd | Drivers          │
│ Filesystem | Container Runtime            │
│ Security | Boot | Update | KDE/KWin*       │
└───────────────────────────────────────────┘
* KDE/KWin 主要用于 Argon
```

以上是逻辑分层，服务层和工作负载层的具体进程可部署于不同隔离环境中。

### 3.1 PsiOS Host Core

负责操作系统必须具备的基础能力：

- 系统启动、安装、升级和回滚。
- Linux 内核、硬件驱动与设备管理。
- 容器运行环境引导。
- 文件系统、挂载和存储驱动。
- 本机身份、权限与特权操作代理。
- 网络和系统服务基础管理。
- 宿主级健康监控和恢复。

设计原则：宿主底座保持精简、可信、可恢复。

### 3.2 PsiOS System API

统一管理系统资源、权限及操作。

建议建立版本化 API 契约，例如 `psios.v1`，并将资源划分为：

| 领域 | 主要资源对象 |
|---|---|
| 系统 | Node、Device、Process、User |
| 应用 | Application、Service、Deployment、Job |
| Agent | Agent、Session、Skill、Task |
| 存储 | Pool、Volume、Snapshot、Backup |
| 数据 | Dataset、Asset、View、Index |
| 集群 | Cluster、Member、Workload、Placement |
| 安全 | Principal、Capability、Grant、Secret |

部分资源仅在对应可选服务安装后可用，不要求宿主提前启动所有功能模块。

## 四、Agent-Native 核心架构

这是 PsiOS 最重要的差异化部分。

### 4.1 统一 Agent 系统

将 Agent 系统划分为四个独立部分：

**Agent Service Bus**

负责 Agent 注册、发现、通信、状态和能力协商，不依赖特定模型或框架。

**Agent Runtime**

执行 PsiOS 原生 Agent，管理上下文、模型调用、任务、工具和执行状态。

**Agent Compatibility Layer**

允许第三方 Agent 通过标准协议、CLI、SDK 或适配器接入 PsiOS。

优先研究和逐步支持 MCP、A2A、ACP、AG-UI、OpenAPI 等适合不同用途的接口，而不是要求第三方 Agent 采用 PsiOS 自有框架。

**Tool & Capability Gateway**

提供对系统能力的受控访问。

例如：

- 文件读取、写入、搜索。
- 应用安装、启动、停止。
- 存储检查、快照、备份。
- 任务调度、GPU 资源申请。
- 桌面观察与操作。
- 集群任务提交。
- 外部服务和网络访问。

### 4.2 模型层独立

模型推理能力不应与 Agent Runtime 强耦合。

支持：

- 本地 CPU/GPU 模型。
- 局域网模型服务器。
- 集群中的远程模型。
- 云端模型 API。
- 不同 Agent 使用不同模型提供者。

PsiOS 的原生 Agent 体验可以通过远程模型实现，不要求 Helium 等精简版本安装大型模型。

### 4.3 Skills 体系

Skills 定义 Agent 可以使用的能力、操作说明和执行入口。

应区分：

- **Skill 描述**：声明式说明、调用约定与使用文档。
- **Tool 实现**：实际执行操作的程序、API 或服务。
- **Capability 授权**：决定谁可以使用哪些能力。
- **Sandbox**：限制代码执行和系统资源访问。

不能将 Skill 文本或提示词视为安全边界。

第三方 Skill 应支持导入、校验、权限审查、版本管理和卸载。

### 4.4 Computer Use

将 Computer Use 设计为系统级服务，而不是某个 Agent 私有的截图和鼠标插件。

操作优先级建议为：

1. 原生系统 API。
2. 应用语义接口和无障碍接口。
3. 浏览器自动化。
4. 截图、视觉定位、键鼠模拟。

对于 Argon，以 KDE Plasma/Wayland 为主要集成环境。

第三方 Agent 默认使用隔离会话或明确授权的桌面会话，不应天然获得任意读取屏幕和操控键鼠的能力。

Neon 支持按需创建无头图形会话；Helium 通过可选图形后端实现相关功能。

### 4.5 Agent 安全策略

所有 Agent，无论原生还是第三方，均必须经过统一权限检查。

重点包括：

- Agent 独立身份。
- 按资源与操作授权。
- 有有效期、可撤销的能力令牌。
- 凭据不直接暴露给模型上下文。
- 危险操作需要可配置审批。
- 所有关键执行过程可审计。
- 可恢复操作优先保留回滚路径。

## 五、应用与容器体系

### 5.1 总体原则

**所有可安装的普通应用、第三方服务、Agent 执行环境及可选系统服务，原则上都使用隔离运行机制。**

但 PsiOS Host Core、内核、驱动、KWin 和必要的系统特权代理保留在可信宿主中。

### 5.2 运行环境

| 类型 | 建议执行方式 |
|---|---|
| 后端服务 | OCI 容器 |
| 数据库、模型服务 | OCI 容器 |
| Agent 和可执行工具 | OCI 或强化沙箱 |
| 桌面应用 | Flatpak 优先 |
| 开发环境 | 开发容器 |
| 系统底层组件 | 原生宿主服务 |
| 纯声明式 Skills | 元数据，不必拥有独立容器 |

OCI Runtime 与 Flatpak 应共享 PsiOS 的应用身份、管理入口及权限映射，但不必实现相同的底层沙箱机制。

### 5.3 Application Manager

应用管理器统一负责：

- 安装、更新和卸载。
- 版本、依赖和制品签名。
- 启动、停止、重启。
- 自动恢复和健康检查。
- 资源限制与设备分配。
- 数据卷与网络配置。
- 权限声明和审批。
- 日志、事件和运行状态。

每个应用由统一清单描述，实际由适合的 Runtime Driver 执行。

### 5.4 应用和数据分离

应用镜像与持久数据必须独立管理。

升级或替换容器不应自动删除用户数据。

对于数据库等有状态服务，需要区分应用版本回滚与数据模式回滚；不能假设只回退容器就能安全恢复数据。

## 六、存储与数据基础设施

### 6.1 分为三个层级

**第一层：Host Storage**

负责磁盘、分区、文件系统、挂载、加密和底层设备管理。

**第二层：PsiOS Storage Service**

统一管理存储池、卷、持久化数据、快照、备份和对象访问等逻辑资源。

**第三层：Data Services**

提供数据集、数据导入、处理、索引、搜索、知识库和相关任务流水线。

三层有清晰边界，避免将完整数据引擎写入宿主核心。

### 6.2 存储抽象

建议定义以下核心对象：

| 对象 | 作用 |
|---|---|
| StoragePool | 管理一组可分配的存储资源 |
| Volume | 为应用提供持久化空间 |
| Object | 提供对象数据访问 |
| Snapshot | 表示一致性恢复点 |
| Backup | 管理可独立恢复的数据副本 |
| StorageDriver | 适配具体文件系统或存储后端 |

支持 SSD、HDD、本地卷、远程存储和未来的集群存储。

初期先实现可靠的单机持久存储，不直接承诺跨节点透明共享文件系统。

不同后端支持的快照、配额和复制能力可不同，应显式声明功能支持情况。

### 6.3 数据集管理系统

数据集管理纳入 PsiOS 主线，但作为可选安装服务。

数据集基础结构采用此前确定的字段契约：

| 字段 | 含义 |
|---|---|
| `uid` | 稳定唯一标识 |
| `name` | 可选名称 |
| `content` | 主内容 |
| `tag` | 分类标签 |
| `score` | 评分 |
| `vector` | 可选向量 |
| `extra_data` | 可选通用 JSON 元数据 |

必须支持按照 `extra_data` 的 JSON 路径或表达式进行精确查询。

数据集服务负责导入、验证、索引、查询、快照、版本与流水线任务。

应允许大型逻辑内容作为一条原始记录保存，例如书籍或代码仓库；索引时可以单独切块，但不应强制破坏原始记录的逻辑边界。

### 6.4 知识库作为数据集视图

知识库不是另一套独立原始数据副本。

它是从主数据集中选择部分表、字段和记录后，建立检索索引的可选服务。

```text
主数据集
   ├── 常规查询
   ├── 子集 / 过滤视图
   │      ├── 全文索引
   │      ├── 向量索引
   │      └── 混合检索
   └── 数据处理与版本管理
```

知识库使用稳定数据 ID 与主数据集版本，索引独立更新，尽可能避免重复保存原文。

Embedding 模型应由独立模型服务或能力提供者负责，数据系统只通过接口调用，不与具体模型绑定。

### 6.5 可选部署

未安装数据集或知识库服务时：

- PsiOS Core 正常运行。
- Agent Runtime 正常运行。
- 普通应用正常运行。
- 基础存储服务正常运行。
- 不要求常驻数据引擎或搜索索引服务。

## 七、集群与分布式运行

### 7.1 集群基本原则

所有 PsiOS 节点都可以独立运行，也可以加入集群。

加入集群后仍保留本机身份、本机权限和独立恢复能力。

集群 Controller 是可配置角色，不是新的发行版。

### 7.2 核心模块

**Node Manager**：管理节点注册、身份、健康、资源和心跳。

**Cluster Controller**：维护集群配置、节点成员关系和全局资源视图。

**Scheduler**：按照 CPU、内存、GPU、存储位置和策略安排任务。

**Task Broker**：管理跨节点任务领取、执行结果、重试和失败恢复。

**Service Discovery**：查找跨节点的模型、Agent、应用和系统能力服务。

**Storage Federation**：通过统一接口访问节点存储，后续再引入复制和迁移机制。

### 7.3 分阶段演进

第一阶段支持节点加入、身份认证、服务发现与远程任务。

第二阶段增加资源调度、故障恢复、多节点 Agent 协作。

第三阶段研究高可用控制面、数据副本、自动迁移与高级存储调度。

集群管理元数据、用户数据与应用状态应采用不同的一致性和恢复策略，不强制用一套复制机制处理全部内容。

## 八、桌面与 PsiOS Shell

### 8.1 KDE Plasma

Argon 以 KDE Plasma 为主要桌面环境。

保留完整的传统 Linux 桌面功能，包括窗口管理、文件管理、多显示器、通知和原生应用交互。

PsiOS 不重新开发一套替代 KDE 的完整桌面环境。

### 8.2 PsiOS Shell

PsiOS Shell 是统一管理 WebUI。

重点提供：

- 系统与资源概览。
- 应用管理。
- Agent 对话、任务及操作记录。
- 存储和数据服务管理。
- 集群节点与计算任务。
- 用户、安全和权限配置。
- 系统日志、更新和恢复入口。

PsiOS Shell 在 Helium、Neon、Argon 中共用主要前端代码。

Argon 可以通过 KDE 原生入口或桌面窗口集成 Shell，但 Shell 本身不替代 Plasma。

### 8.3 多终端一致性

同一操作应尽可能共享后端 API：

- WebUI。
- 命令行。
- SDK。
- 原生 Agent。
- 第三方 Agent。

避免 WebUI 和 Agent 分别实现一套管理逻辑。

## 九、XeLab 代码迁移与复用

旧 XeLab 仅作为代码来源。

需要以本地 Forgejo 最新 HEAD 为审计基线，而不是依据旧 GitHub 快照判断实现情况。

优先评估：

| 模块 | 迁移方向 |
|---|---|
| Task Engine | 优先复用执行、重试、状态机 |
| Broker | 复用队列与任务分发机制 |
| OCI Runtime | 复用容器生命周期与隔离能力 |
| Event Store | 复用事件持久化和恢复机制 |
| HostService | 拆分为 PsiOS 受控宿主能力 |
| Identity / Auth | 复用成熟实现，重新定义权限对象 |
| Storage | 复用可靠的配额、校验、备份等模块 |
| SDK | 选择可独立抽取的协议与客户端组件 |
| WebUI | 参考功能与设计，重新组织页面 |

每个模块必须经过依赖审计、边界重划、测试及独立化改造，才可进入 PsiOS Core。

对于耦合旧 XeLab 平台契约过深的模块，允许直接重写。

## 十、建议技术基线

以下属于候选技术，而非已经确定的全部选型。

| 子系统 | 候选技术 |
|---|---|
| 内核 | Linux |
| 服务管理 | systemd |
| 核心服务 | Rust 优先，按需使用 C/C++ |
| 系统镜像与更新 | bootc / OSTree 等事务式更新方案 |
| OCI | OCI-compatible Runtime，评估复用原 XeLab 实现 |
| 桌面应用 | Flatpak |
| 桌面 | KDE Plasma + Wayland |
| 桌面能力 | XDG Portals、PipeWire、AT-SPI、libei |
| 进程通信 | Unix Socket、D-Bus、gRPC/HTTP（按边界选择） |
| 集群通信 | 加密且双向认证的节点通信 |
| 数据存储 | 开放格式与可替换后端 |
| API | 版本化 Schema 与 SDK |
| CI | 构建、单元测试、集成测试、VM 和真实设备验收 |

系统基础发行版、默认文件系统、容器执行后端及升级机制都需要先完成可行性验证，再冻结选型。

## 十一、开发路线与里程碑

PsiOS 不设置强制完成日期，采用阶段目标和验收门槛推进。

| 阶段 | 主题 | 核心交付物 |
|---|---|---|
| M0 | 架构冻结与代码审计 | 架构文档、API 草案、XeLab 复用清单、技术验证 |
| M1 | 可启动系统 | PsiOS Host Core、最小系统镜像、安装与恢复 |
| M2 | 应用和基础服务 | OCI 管理、权限、持久卷、Shell、统一资源 API |
| M3 | Agent 原生化 | Agent Runtime、Skill、Tool Gateway、第三方 Agent 接入 |
| M4 | 三版本与集群闭环 | Helium/Neon/Argon 构建、节点加入、任务调度、KDE Computer Use |
| M5 | 数据与高级系统服务 | 可选 Dataset、Knowledge、备份、存储增强 |
| M6 | 系统化测试与发布 | 更新回滚、安全审查、故障恢复、Beta/稳定版准备 |

### M0 验收

- 已明确核心组件边界和系统资源模型。
- 已审计当前 XeLab 代码。
- 已建立可构建、可测试的仓库。
- 已验证 OS 镜像、容器及权限方案可行。

### M1–M2 验收

- 目标设备或虚拟机能够启动 PsiOS。
- 能够安装、启动、更新、删除一个 OCI 应用。
- 系统重启后应用持久数据存在。
- 更新失败有明确恢复方案。
- Shell 可以查询基础系统状态。

### M3 验收

- 原生 Agent 可以调用系统工具完成一项真实任务。
- 第三方 Agent 能通过受控接口完成同类任务。
- 权限拒绝、撤销和审计真实有效。
- Agent 失败不导致宿主异常退出。

### M4 验收

- 三个发行版均可运行原生 Agent、接受第三方 Agent 接入并加入集群。
- Neon 可以执行远程提交的容器任务。
- Argon 可以进入完整 KDE 桌面。
- Computer Use 可以在授权下观察和操作指定会话。
- 网络或控制面故障不会无故破坏节点已有持久数据。

### M5–M6 验收

- 可选数据服务能独立安装和卸载。
- 主数据集与知识库索引之间不存在不必要的原文重复。
- 备份、恢复、快照及版本一致性可验证。
- 三种版本能够通过自动化回归和基本真实硬件验收。
- 发布镜像、API 兼容策略及安全更新流程完整。

## 十二、项目代码组织建议

```text
PsiOS/
├── core/           # Host Core与基础系统能力
├── api/            # 版本化系统资源与能力契约
├── runtime/        # OCI、Flatpak与执行后端适配
├── agent/          # 原生Agent与第三方兼容层
├── services/       # 存储、任务、模型、数据等服务
├── cluster/        # 节点管理、发现、调度
├── shell/          # 统一WebUI
├── desktop/        # KDE集成与Computer Use
├── editions/       # Helium / Neon / Argon配置
├── packages/       # 应用与可选系统服务清单
├── images/         # 系统镜像构建
├── tests/          # 自动化测试和兼容测试
└── docs/           # 架构、API和设计决策
```

上述目录是逻辑拆分草案，最终可根据 Rust workspace、镜像工程和构建依赖关系调整。

## 十三、当前需要确定的架构决策

| 优先级 | 待决问题 | 建议方向 |
|---|---|---|
| P0 | OS 基础发行版和镜像构建 | 先验证 bootc 等方案，不直接绑定单一发行版 |
| P0 | Core 与容器服务的边界 | 最小宿主 + 权限代理 + 隔离工作负载 |
| P0 | Agent 能力与权限模型 | 与具体 Agent 框架独立 |
| P0 | 系统资源及 API Schema | 统一版本化资源模型 |
| P0 | XeLab 可复用模块 | 基于 Forgejo 最新代码逐模块审计 |
| P1 | 默认容器执行后端 | 评估复用 XeLab OCI Runtime 与现成方案 |
| P1 | 默认存储后端 | 先定义存储抽象，再选基础文件系统 |
| P1 | 集群一致性与控制面 | 单机优先，逐步实现多节点 |
| P1 | KDE 与 Computer Use 接口 | 优先使用现有 Wayland/Portal 能力 |
| P2 | Dataset 和 Knowledge 引擎 | 可选服务，不成为 Core 硬依赖 |
| P2 | 高级分布式存储 | 在单机持久化可靠后推进 |

## 十四、最终架构原则

PsiOS 的长期设计应遵守以下约束：

1. **统一核心，不分裂发行版代码。**
2. **Agent 原生，但不让系统依赖某一个 Agent。**
3. **兼容第三方生态，避免形成封闭框架。**
4. **普通应用与可选服务隔离，宿主维持最小可信边界。**
5. **系统能力统一授权，不允许 Agent 绕过权限模型。**
6. **数据独立于应用生命周期，优先保证完整性和可恢复性。**
7. **集群是系统基础能力，但单机运行不能依赖集群在线。**
8. **桌面采用 KDE，PsiOS Shell 负责统一管理界面。**
9. **已有 XeLab 代码按模块复用，不继承历史设计负担。**
10. **以完整可验证的工作闭环推进，而非单纯堆积功能。**

**项目最终目标：** 构建一个既能作为常规 Linux 操作系统独立使用，又能让 Agent 安全、原生地操作系统、应用、数据与集群资源的开放式操作系统平台。
